# ADR-006：退款模型

- 狀態：已採用（P1）
- 相關：規格 F11、V07、T05–T07、T34；決策 D16、U7–U12

## 背景

需求確認時決定「退款當天沖回原費用科目，並連結原交易」。
退款不是收入：網購 800 退 800，網購這個月的淨支出應該是 0，而不是支出 800、收入 800。
跨月退款則讓退款月份的支出出現負數，這是正確的（T06）。

## 決定

1. **退款是獨立的 `REFUND` 交易**，用 `related_txn_id` 連到原交易；只能對有效（POSTED、未刪除）的
   `EXPENSE` 交易退款（`REFUND_ORIGINAL`）。
2. **只沖回原交易唯一的 MAIN 分錄。** 退款固定兩筆分錄：
   - 退回帳戶 +金額（退回現金／銀行；退回信用卡就是欠款減少）
   - 原交易 MAIN 的費用科目 −金額（line_role = MAIN）
   支出科目、商家、`exclude_from_budget` 從原交易帶入，使用者不能選；退款方式可以和原交易不同。
3. **手續費（FEE）、分期利息（INTEREST）不自動退款**（T34）。真的有退手續費的情況用 MANUAL 交易處理。
4. **金額上限（V07）**：同一原交易的有效退款（POSTED、未刪除、MAIN 分錄）加總不能超過原交易 MAIN 金額；
   修改退款時排除自己。已刪除的退款不算已退。
5. **日期**：退款日期不能早於原交易（`REFUND_DATE`）。
6. **不支援原幣**（U12）。外幣交易超額退款（匯差）用 MANUAL 處理。
7. **退款生命週期的鎖定**（D16、U10、U11）：
   - 原支出已有有效退款時不能刪除（`REFUND_EXISTS`），要先刪退款。
   - 原支出的 MAIN 科目、`exclude_from_budget` 不能改；MAIN 金額不能低於已退總額；
     日期不能晚於最早一筆有效退款（`REFUND_LOCKED`）。商家、備註、付款方式、手續費、利息可以改。
   - 退款不能改連到其他原交易（`REFUND_LOCKED`）。
   - 不做「原交易修改後同步更新退款」的機制。
   - 還原退款時重新檢查原交易仍有效、日期與金額上限（原交易可能在退款刪除期間被修改過）。

## 考慮過的替代方案

- **退款記成收入**：會讓支出與收入同時膨脹，預算和月報都失真。
- **直接修改原交易金額**：失去「何時退款、退到哪裡」的資訊，跨月退款也會改到已經過去的月份。
- **按比例沖回 MAIN、FEE、INTEREST**：大部分退款不會退手續費，自動拆分反而要再手動修正。
- **原交易修改時自動同步退款**：邏輯複雜，而且很難判斷使用者的真正意圖；改成鎖定會破壞一致性的欄位。

## 後果

- 正面：費用科目、預算、月報自然反映淨支出；每筆退款都能追溯到原交易。
- 正面：鎖定規則保證「已退金額 ≤ 原交易金額」這個關係不會因為修改而被破壞。
- 代價：要大幅修改已有退款的原交易時，得先刪除退款、改完再重新退款。
