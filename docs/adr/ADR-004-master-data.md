# ADR-004：主資料：系統科目識別與付款方式

- 狀態：已採用（P1）
- 相關：規格 6.1–6.3；決策 D2、D4、D9、P1、P5、S1–S11

## 背景

科目、帳戶、付款方式都是使用者可以改的主資料，不能 hard-code 在程式裡。
但有兩個地方程式一定要認得特定的資料：

1. 期初餘額的對方科目「期初權益」、帳務調整的對方科目「帳務調整」。
2. 支出時錢實際從哪個帳戶出去。使用者用的是「LINE Pay」「台灣Pay」「郵局簽帳卡」，
   但它們都扣同一個郵局帳戶；「聯邦信用卡」則是負債帳戶。

## 決定

1. **系統科目用 `accounts.system_key` 識別**（nullable、UNIQUE），目前只有 `OPENING_EQUITY`、`ADJUSTMENT`。
   程式用 `system_account(db, key)` 找科目，不依賴固定 id 或科目代碼；找不到時丟 `MissingSystemAccount`
   （系統／主資料異常，不是使用者輸入錯誤）。
   系統科目只能用在對應的交易類型（`SYSTEM_ACCOUNT`），也不能停用。
2. **付款方式和帳戶分離。** `payment_methods` 只是付款管道，各自對應一個資產或負債帳戶（`account_id`）。
   支出時由 `transactions.py` 把付款方式解析成帳戶，再交給 builder；交易表頭保留 `payment_method_id`，
   之後可以分析「用哪個管道付」。預設付款方式只用 `payment_methods.is_default`（同時只能有一個）。
3. **收入不使用付款方式**：收入直接指定收款帳戶（P5），因為收款帳戶不是付款管道。
4. **轉入信用卡就是信用卡繳款**（D9）：轉帳的轉入帳戶是信用卡時，自動改成 `CARD_PAYMENT`，
   不會被當成一般轉帳，也不可能計入支出。
5. **初始資料用 YAML + 可重複執行的 seed**（`scripts/seed_master_data.py`）：只新增缺少的資料，不覆寫、不刪除；
   結構衝突整批中止。正式科目表與測試用科目表分開。

## 考慮過的替代方案

- **固定 id（例如 id = 1 是期初權益）**：資料庫重建或匯入時 id 可能改變，錯了也不會報錯。
- **用科目代碼識別系統科目**：代碼是使用者可見、可規劃的編號，不應該同時承擔程式識別的責任。
- **把 LINE Pay 等做成子帳戶**：會讓郵局的實際餘額被拆散，和銀行對帳變困難。

## 後果

- 正面：使用者可以改名、調整科目表，不會影響程式找系統科目。
- 正面：換付款帳戶（例如 LINE Pay 改綁別的帳戶）只要改一筆主資料。
- 代價：每次記支出都要多一次付款方式查詢；對個人帳可以忽略。
