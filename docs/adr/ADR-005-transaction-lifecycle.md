# ADR-005：交易生命週期（修改、軟刪除、還原）

- 狀態：已採用（P1）
- 相關：規格「寬鬆修改模式 + 稽核紀錄 + 軟刪除」；決策 D6、D12、D14、U1–U6、U13、U14

## 背景

個人記帳常常記錯：金額打錯、科目選錯、日期記錯。規格選擇「寬鬆修改模式」：
交易可以直接修改或刪除，但每次異動都要留下稽核紀錄，刪除可以還原。

## 決定

1. **交易類型不能改**（`TXN_TYPE_IMMUTABLE`）。支出改成轉帳，分錄形狀完全不同，應該刪除後重記。
2. **修改 = 整批替換分錄。** 驗證通過後刪掉舊分錄、寫入新分錄（line_no 重新從 1 編）；
   表頭的 `status`、`source`、`source_ref` 不變。不做逐筆分錄的差異更新。
3. **軟刪除。** 只設定 `deleted_at`，分錄保留，之後由 `active_postings()` 自動排除。
   已刪除的交易要先還原才能修改（`TXN_DELETED`）。
4. **還原會重新檢查**「放回帳上會不會壞」：借貸平衡、同一帳戶期初是否已被重新設定（D12）、
   退款的原交易與金額上限、發票號碼是否已被其他交易使用（V08）。
   還原不是重新輸入，所以**不重跑** V04（科目已停用也可以還原）、V10、V11。
5. **D14：停用的科目只限制新增或被改動的分錄。**
   - 分錄身分 = `(account_id, amount, line_role, original_currency, original_amount_minor)`，不含 memo。
   - 用 `Counter`（多重集合）比對新舊版本：同一身分的分錄多出一筆，多出來的那筆就是新分錄。
   - 付款方式、商家沒換就不檢查是否停用。
6. **確認與提醒只看改變的部分。** V10（大金額）只在交易金額改變時重問；V11（未來日期）只在日期改變時重問；
   V13（負餘額）用「現在餘額 − 舊影響 + 新影響」，舊／新影響只在各自日期 ≤ 今天時計入。
7. **稽核**：每次 CREATE／UPDATE／DELETE／RESTORE 寫一筆 `audit_logs`，before／after 是完整快照
   （表頭 + 每筆分錄，含科目代碼），和異動在同一個資料庫交易內。

## 考慮過的替代方案

- **不可變帳本（只能用沖銷交易更正）**：會計上最嚴謹，但個人記帳每改一個錯字就多兩筆交易，使用體驗太差。
- **逐筆分錄差異更新**：保留分錄 id，但邏輯複雜很多，而且分錄沒有被外部引用，保留 id 沒有好處。
- **硬刪除**：最簡單，但無法還原，稽核紀錄也只剩快照。
- **還原時重跑完整驗證**：科目停用後就永遠無法還原舊交易，違反 D14 的精神。

## 後果

- 正面：任何修改都可追溯，刪錯可以還原；餘額永遠由分錄即時計算，沒有狀態要同步。
- 代價：已刪除交易的分錄留在資料庫裡，帳平檢查要刻意包含它們（ADR-002 的例外）。

## 已知限制與未來考量

- **併發（已知限制）**：V07、D12 等規則是「先檢查、再寫入」，兩個請求同時送出時理論上可能都通過檢查。
  系統是單一使用者、SQLite、日常個人記帳，實際上不會發生，因此 P1／P2 不加入 `BEGIN IMMEDIATE`、額外鎖或交易抽象；
  真的出現需求時再處理。
- **草稿交易（V1.5）**：P1 只會建立 POSTED 交易。`update`／`soft_delete`／`restore` 目前不檢查 `status`；
  V1.5 加入草稿與確認入帳時，要決定草稿能否用這些操作（例如新增 `TXN_NOT_POSTED`）。
