# P2 每日記帳：決策紀錄

P2 範圍：規格 F15–F19、F22–F25。這份文件只記錄**已拍板、已實作**的決策。

## Step 2：商家、V12、憑證、V08、重複送出

- **商家（M2）**：快速記帳輸入商家名稱；先比對別名（`alias_normalized`），再比對正規化後的標準名稱；
  找不到就以輸入名稱建立新商家，不建立別名。商家必須在交易寫入前 commit（P1 Q3），
  所以交易被 422／409 擋下時可能留下未被引用的商家；這是主資料殘留，不是帳務錯誤，接受。
- **商家名稱正規化**：只做全形 ASCII／全形空白轉半形、去除空白、轉小寫；不使用 NFKC。
  `merchants` 沒有 `name_normalized` 欄位，標準名稱的比對在 Python 端進行（不新增 migration）。
- **V12**：有效 EXPENSE、同日期、同商家、同 MAIN 金額 → 確認（409）。只比對 EXPENSE；
  手續費、利息不影響；從 `active_postings()` 查詢；修改時排除自己；還原不重跑。
- **發票號碼**：Web 只做去空白、轉大寫，並移除「2 個字母-8 位數字」中間的單一連字號；
  格式與重複由 P1 的 V08 判斷（新增、修改共用；修改排除自己）。寫入時撞到部分唯一索引，
  rollback 後以「該號碼是否被其他未刪除交易占用」判斷，只把這種情況轉成 V08，其他 IntegrityError 原樣拋出。
- **重複送出（決策 A）**：Web 表單的一次性權杖寫入 `source = MANUAL`、`source_ref = "submit:<token>"`，
  沿用既有 `UNIQUE(source, source_ref)`，不新增資料表或 migration。同一個權杖第二次送出不驗證、
  不寫入、不寫稽核，回傳第一次建立的交易；軟刪除後權杖仍被占用。沒有權杖的 POST 回 422。

## Step 3：交易列表與搜尋（GET /txn）

- **列表顯示金額 = 交易規模（magnitude）**：該交易所有正數分錄的加總，所有 txn_type 同一個定義，
  一律為正數，搭配交易類型標籤顯示，不用正負號或紅綠色暗示支出、收入。
  EXPENSE 的 magnitude 包含 MAIN、FEE、INTEREST；這和 V12 只比對 MAIN 不衝突：
  V12 判斷「是不是同一筆主要消費」，magnitude 表示「整筆分錄的規模」。
- **搜尋摘要（F1）**：涵蓋全部符合條件的結果（不是目前這一頁）。
  `expense_net = SUM(EXPENSE 科目分錄 amount)`，不取絕對值，只有退款時可以是負數；
  `income_total = -SUM(INCOME 科目分錄 amount)`，有收入時才顯示。依科目類別計算，不依 txn_type 特判：
  轉帳、繳卡費沒有費用分錄所以不算支出，轉帳手續費是費用分錄所以算支出。
- **查詢**：從 `active_postings()` 依交易分組成「一筆交易一列」的子查詢，再做篩選、筆數、分頁與合計，
  避免 postings join 造成筆數膨脹；排除條件不在其他地方重寫。
- **條件**：日期區間（含頭尾）、商家（`merchants.resolve()`，正規化後完全相同，含別名；只讀，不建立商家）、
  金額範圍（比對 magnitude，含頭尾）。不做交易類型篩選、商家部分比對、即時搜尋。
  條件放 query string；完全沒帶條件時預設本月；欄位出現但空白代表不限。
  日期或金額格式錯誤、日期或金額範圍顛倒，在 Web 邊界回 422，不進 P1 validation。
- **分頁**：offset 分頁，每頁 50 筆，排序 `txn_date DESC, id DESC`。

## Step 4A：交易明細、修改、刪除、還原

- **明細 `GET /txn/{id}`**：所有類型、包含已刪除的交易（規格 5.4 允許「已刪除」檢視）。分錄不顯示借／貸或帶正負號的金額，
  由 service 依科目正常餘額方向（`NORMAL_SIGN`）換算成「科目 + 增加／減少 + 金額」，必要時加分錄角色（手續費、分期利息）。
- **修改只限「快速記帳格式」的 EXPENSE**：未刪除、POSTED、剛好 MAIN + 付款兩筆分錄、沒有 FEE／INTEREST、
  沒有外幣資料、`exclude_from_budget = False`。其他交易不提供修改，直接 POST 也由伺服器擋下（NOT_EDITABLE，422）。
  理由：Web 表單只有快速記帳的欄位，拿來修改其他形狀的交易會默默刪掉手續費、利息、外幣或改掉「不計入預算」。
  這是 4A 唯一新增的判斷；帳務規則（V08、V10–V12、REFUND_LOCKED、TXN_TYPE_IMMUTABLE、TXN_DELETED）仍全部由 P1 負責。
- **送出權杖**：修改不使用權杖（修改不會新增交易）；`parse_expense(require_submission_token=False)` 只給修改使用，
  新增（POST /txn/new）仍必填，缺少或格式錯誤回 422。
- **軟刪除與還原**：`<details>` 展開後才顯示刪除按鈕；`POST /txn/{id}/delete`、`/restore` 呼叫 P1 lifecycle，
  成功後回到該交易明細；P1 擋下時（REFUND_EXISTS、TXN_DELETED、V08、OPENING_EXISTS、REFUND_ORIGINAL、V07）回 422 並顯示原因。
  還原不重跑 V10／V11／V12，不需要確認。不做 hard delete。
- **NotFound → 404**：只在 txn router 對應，不做全域框架。HTMX 請求用 HX-Redirect 導到明細網址顯示 404 頁。
- **修改、還原成功後的提醒**：P1 回傳的 `PostResult.notices`（例如 V13 負餘額）不能被 Web 吞掉。
  成功後不導頁，直接回傳明細內容並顯示提醒：還原換掉 `#txn-detail`；修改用 `HX-Retarget: main.container`、
  `HX-Push-Url: /txn/{id}` 換成明細頁。不新增 flash 訊息機制。刪除沒有提醒，維持導頁。

## Step 4B：異動紀錄與已刪除交易（只讀）

- **異動紀錄**放在交易明細頁底部，`<details>` 預設收合，由舊到新（`occurred_at, id`；`occurred_at` 只到秒，用 id 保證順序）。
  只顯示時間、動作（建立／修改／刪除／還原）與可讀摘要；不顯示原始 before／after JSON，也不顯示 user_id（資料仍保留）。
- **UPDATE 摘要**：逐一比較日期、金額（交易規模，從快照的分錄計算）、商家、付款方式、備註、憑證類型、發票號碼、
  不計入預算。分錄「有沒有變」用完整的分錄內容比較（除 line_no 外全部欄位，含 memo、原幣，不在乎順序）；
  科目、金額或分錄角色有變時顯示「分錄：前 → 後」（科目代碼 + 名稱 + 增加／減少 + 金額），
  只有 memo、原幣這類內容變了時顯示「分錄內容已變更」，不會誤報「內容沒有變更」。
- **名稱是「現在」的名稱，不是歷史名稱**：稽核快照只存 id 與科目代碼（不改 P1 快照與 schema），
  所以科目改名後舊紀錄也顯示新名稱；一律保留快照裡的科目代碼（例如「5101 正餐」）。
  科目查不到時退回科目代碼，商家、付款方式查不到時顯示 #id。
- **已刪除交易**：獨立的唯讀頁 `GET /txn/deleted`（不用 `/txn?deleted=1`，避免汙染有效交易的搜尋與合計路徑）。
  只列 `deleted_at IS NOT NULL`，最近刪除的在前（`deleted_at DESC, id DESC`），每頁 50 筆，只顯示筆數，
  沒有篩選、沒有任何金額合計。每列的金額只用該交易自己的分錄計算、僅供顯示，不提供給餘額、合計、報表、預算。
  還原沿用 Step 4A 的已刪除明細。

## Step 5A：收入、轉帳新增與類型切換

- **只做新增**：`/txn/new?type=expense|income|transfer`，預設支出；不合法的 `type` 一律當成支出，畫面上的
  hidden `txn_type` 一定是合法值。POST 依 `txn_type` 分派，不合法的值直接 422（「表單已失效」），不呼叫 orchestration。
  收入、轉帳的修改留到 Step 5B。
- **類型切換**：一般連結（`href`）可整頁切換；HTMX 用 `hx-get` + `hx-push-url` 換掉整個 `#txn-new`，網址更新、
  重新整理保留類型。只帶日期與金額（`hx-include`），其他欄位不保留、不做跨類型對應。整塊替換，所以 DOM 裡只會有
  新表單的那一個送出權杖。
- **收入表單**只有日期、金額、收入科目、收款帳戶、備註；不提供商家。**轉帳表單**有轉出、轉入、手續費（選填，
  收合）、日期、備註。收款／轉出／轉入都沒有預設值，支出的預設付款方式不套用到其他類型。
- **選項**：收入科目 = 啟用中的 INCOME 末層；收款、轉入 = 啟用中的 ASSET／LIABILITY 末層（轉入含信用卡）；
  轉出 = 同上但不列信用卡；手續費 = 啟用中的 EXPENSE 末層。轉出不列信用卡只是不提供一定會被 P6 擋下的選項，
  規則仍由 P1 檢查（直接送出也會被擋）。
- **一次性送出權杖共用**：`transactions._post_once()` 讓支出、收入、轉帳（含 D9 自動改成的繳卡費）都用同一套
  `source=MANUAL`、`source_ref=submit:<token>`、UNIQUE 並發處理。`submission_token=None` 時維持原本的
  `ledger.post`（service 呼叫端不需要權杖）；Web 新增一律必填，缺少或格式錯誤回 422 並換新權杖。
- **繳卡費（D9）**：使用者操作的是「轉帳、轉入信用卡」，Web 不判斷會計類型。成功後依 transaction_id 讀回實際
  類型與交易規模顯示（「已儲存：繳卡費 2,000 元」）；列表與明細沿用既有的「繳卡費」標籤。
  P1 回傳的 `card_account_id` 欄位錯誤集中對應到畫面的 `to_account_id`（`ISSUE_FIELD_TO_FORM`），只是顯示位置。
- **儲存並記下一筆**：收入保留日期 + 收款帳戶；轉帳保留日期 + 轉出帳戶；其他清空、換新權杖、焦點回到金額。
- **確認與提醒**沿用 P1（V06、V10、V11、V13、TXN_STRUCTURE）；422 保留輸入與同一個權杖，409 確認畫面帶著
  `txn_type`、全部欄位與同一個權杖；成功顯示 `PostResult.notices`。
- 沒有拆 `app/routers/txn.py`（純重構不混進 5A），沒有 migration。

## Step 5B：修改收入、轉帳、繳卡費

- **表單依原交易類型決定**（不信任送來的 `txn_type`）：收入 → 收入表單；轉帳、繳卡費 → 轉帳表單。
  繳卡費也送 `TransferForm`，D9 由 P1 在每次 update 重新判斷；草稿類型和原交易不同時由 P1 回
  `TXN_TYPE_IMMUTABLE`（轉帳改成轉入信用卡、繳卡費改成非信用卡都一樣），Web 不繞過、不做類型轉換。
- **修改條件**（`services/txn_edit.py`）：已刪除、草稿不可修改；有商家的收入不可修改（收入表單沒有商家欄位，
  不默默保留看不到的狀態）；表頭有表單沒有的欄位不可修改。分錄用「還原成表單 → P1 builder 重建 →
  完整比對（科目、金額、角色、原幣、memo，不看順序）」判斷，不一致就是 NOT_EDITABLE。
  GET 導回明細並說明原因；直接 POST 回 422，不寫入、不新增稽核。退款等其他類型仍不提供修改。
- **選項過濾**（只是 UX，P1 仍是最終檢查）：修改轉帳時轉出、轉入都不列信用卡；修改繳卡費時轉入只列信用卡、
  不顯示手續費（直接 POST 帶手續費由 P1 回 TXN_STRUCTURE，顯示在頂端）。
- **停用中的目前值（D5，支出一起修正）**：P1 允許沒有變更的分錄繼續使用停用科目（D14），
  所以修改表單的選單會額外列出「這筆交易目前使用、但已停用」的那一個值（標示「已停用」、保持選取）；
  其他停用值不列。目前值取自原交易，不取送來的值。改成另一個停用值仍由 P1 擋下。
- **schema**：新增（`IncomeInput`、`TransferInput`）權杖必填；修改（`IncomeEditInput`、`TransferEditInput`）
  沒有權杖欄位。
- 稽核、原子性沿用 P1：成功只寫一筆 UPDATE（`user_id`、transaction_id、source_ref 不變）；
  任何錯誤整批回滾。沒有判斷「其實沒改」，沿用 P1。沒有 migration，沒有拆 router。

## Step 6：支出的進階欄位（手續費、分期利息、不計入預算）

- **範圍**：支出表單加上收合的「進階」區塊：手續費＋科目、分期利息（分期付款才填）＋科目、不計入預算。
  有值或有錯誤時自動展開；儲存並記下一筆後清空並收合（仍只保留日期與付款方式）。
  沒有「是否分期」勾選框：有填分期利息就代表分期；V1 不輸入期數、每期金額、利率，不建資料表。
- **外幣延後到 V1.5（S03）**：表單沒有原幣欄位，送來也忽略；P1 的原幣能力不動。有原幣的支出明細照常顯示，
  但不開放修改（伺服器端擋下）。
- **帳務完全沿用 P1**：FEE、INTEREST 是費用科目的正數分錄，付款分錄是負的總額；交易規模與支出淨額都包含
  手續費、利息；V10 看完整交易規模；V12 只比 MAIN；分期利息只能刷信用卡（P12，TXN_STRUCTURE）；
  已有退款時不能切換不計入預算（REFUND_LOCKED），手續費、利息仍可改（U10、U11）。Web 只傳值。
- **不計入預算**是表頭旗標，不影響交易列表的支出合計；明細只在「是」時顯示一行。
- **修改條件**：支出改用和 5B 相同的「還原 → ExpenseEntry 重建 → 完整比對」，取代 4A 的手寫格式檢查；
  手續費、分期利息、不計入預算開放修改。仍不開放：已刪除、草稿、外幣、有關聯交易、重建不一致（例如兩筆 FEE）。
- **已知取捨：付款方式改了扣款帳戶**。重建付款分錄時用付款方式「現在」的扣款帳戶；付款方式後來改對應帳戶時，
  重建結果和歷史分錄不同 → 安全地判定不可修改。不為了修改去改寫歷史分錄，也不改 P1 付款方式的生命週期。
  要修改這類交易只能刪除後重記（或日後的多分錄修改）。
- 沒有 migration（欄位都在 0002）。
