# P1 帳務核心：決策紀錄

P1 範圍：規格 F01–F14、F30（P1 適用部分）。這一階段只做後端帳務核心，不做介面。
這份文件只記錄**已拍板、已實作**的決策；尚未實作的項目放在最後的「延後與未來考量」，不代表現有行為。
較大的架構決策另有 ADR（[`docs/adr/`](../adr/)），規則與測試的對照在 [`docs/p1-rules.md`](../p1-rules.md)。

## Step 劃分

| Step | 內容 |
|---|---|
| 1 | Schema：migration `0002`，帳務 10 張表 |
| 2 | 科目主資料：科目表、付款方式、信用卡設定、seed |
| 3 | 帳本骨架：`ledger.post`、`ManualEntry`、`active_postings()`、驗證框架、integrity |
| 4 | 日常交易：支出、收入、轉帳、信用卡繳款 |
| 5 | 特殊交易：期初、帳務調整、薪資 |
| 6 | 交易生命週期與退款 |
| 7 | 收尾：架構守門、文件、規則對照 |

## 核心決策（D1–D16）

- **D1** 五大類只是 enum；`parent_id` 為 NULL 代表第一層科目。
- **D2** `accounts.system_key`（nullable、UNIQUE）識別系統科目，目前只有 `OPENING_EQUITY`、`ADJUSTMENT`（ADR-004）。
- **D3** 最末層 = 沒有任何子科目，不論子科目是否啟用。
- **D4** 預設付款方式只用 `payment_methods.is_default`，settings 不另存。
- **D5** P1 建立 merchants／merchant_aliases 基礎表；credit_card_profiles 建表並實作 M07；帳單週期計算留到 P3。
- **D6** `audit_logs` 由 LedgerService 在同一個資料庫交易內寫入；檢視介面留到 P2。
- **D7** V1 不存分期期數：本金與利息在購買當下全額入帳；期數相關功能延後到 V1.5。
- **D8** 後端支援 `original_currency`／`original_amount_minor`；介面延後。
- **D9** 轉入信用卡負債帳戶 → `CARD_PAYMENT`。
- **D10** 薪資共用 ManualEntry 的多分錄機制，但 `txn_type = PAYROLL`；0 元分錄自動略過。
- **D11** 帳務調整輸入帶正負號的差額，不可為 0。
- **D12** 可以有多筆 OPENING 交易，但同一帳戶只能有一筆有效期初分錄。
- **D13** P1 實作 V01–V07、V09–V11、V13、V15；V08、V12 在 P2；V14 在 P3。
- **D14** V04（停用）只限制新增或實際被改動的分錄；還原允許引用已停用科目。
- **D15** P1 只提供最小查詢：餘額、期間合計、淨資產、帳務調整合計；完整報表在 P3。
- **D16** 原交易有退款時不能刪除；MAIN 金額不能低於已退總額；退款日期不能早於原交易。

其他預設：停用父科目前要先停用全部子科目；P1 只建立 POSTED 交易；integrity 在 P1 只提供 service；
應收／應付（F14）用最末層科目 + 轉帳記錄；手續費科目由使用者指定。

## Step 1：Schema

- Boolean 用 SQLAlchemy Boolean，SQLite 存 0／1 並以 CHECK 限制。
- 額外的資料完整性限制：日期格式 GLOB、發票號碼格式（2 個大寫英文 + 8 位數字）、交易不可自我關聯、
  line_no ≥ 1 且交易內唯一、分錄金額不為 0、`minor_unit ≥ 0`、`credit_limit > 0`。
- 發票號碼在未刪除的交易間唯一（部分唯一索引）。
- 不存在任何餘額欄位（有測試把關）。

## Step 2：科目主資料（S1–S11）

- **S1** 信用卡可以先沒有結帳日設定（profile）；M07 只約束建立或修改 profile 的時候。尚未設定的卡可以正常記帳。
- **S2** 正式科目表 42 個科目；**S3** 資產、負債攤平，不預建空的群組。
- **S4** 科目表用 YAML，只用 `safe_load`；**S5** 幣別只放 USD、JPY，`postings.amount` 本身就是台幣。
- **S6** seed 只新增、不覆寫、不刪除；結構衝突（五大類、子類型、system_key、上層、minor_unit）整批中止。
- **S7** P1 不為主資料異動寫稽核紀錄；**S8** V1 不提供科目搬移。
- **S9** 同一上層下名稱不可重複；**S10** tax_category 只允許最末層。
- **S11** 正式科目表與測試用科目表分開。
- 延伸：付款方式或信用卡設定使用中的帳戶不能新增子科目；扣繳帳戶被引用時不能停用或刪除；
  M01／M03 的「已有分錄」包含草稿與已刪除；主資料規則違反時丟 `RuleViolation(code, message)`。

## Step 3：帳本骨架（Q1–Q11）

- **Q1** 草稿日期用 `date` 物件，寫入時轉成 ISO 字串。
- **Q2** 帳務驗證用 `ValidationResult`（errors／confirmations／notices）；主資料規則用 `RuleViolation`。
- **Q3** `post()` 拒絕 Session 有未提交的變更（`SessionNotClean`），不另建 Unit of Work。
- **Q4** V10 交易金額 = 所有正數分錄加總，「大於」門檻才確認。
- **Q5** 查詢回傳正常餘額方向：資產、費用 = +SUM；負債、權益、收入 = −SUM。報表不 `abs()`、不自行翻號。
- **Q6** ManualEntry 用帶正負號的金額，整數 0 的行自動略過。
- **Q7** `user_id` 在 P1 可以是 None；P2 有登入使用者時必須傳入。
- **Q8** 期初權益只能用在 OPENING，帳務調整只能用在 ADJUSTMENT（`SYSTEM_ACCOUNT`）。
- **Q9** integrity 另外檢查記在非最末層科目的分錄（`NON_LEAF_ACCOUNT`）。
- **Q10** 同一筆交易可以有多筆同科目的分錄；V13 先依科目加總淨變動再判斷。
- **Q11** 架構守門測試。
- 分錄金額的不變條件代碼是 `POSTING_AMOUNT`，不是 V01；V01 由各 builder 檢查使用者輸入。
- `PostingDraft.account_id` 可以是 None（尚未選科目），由 V05 擋下；builder 只做結構轉換。
- V13 與 `balance()` 都以「截至今天（台北日期）」計算；未來日期的交易不影響今天的餘額。
- `large_amount_threshold` 不存在 → 用規格預設 10,000；存在但不是正整數 → `InvalidSetting`，不靜默改用預設值。

## Step 4：日常交易（P1–P12）

- **P1** 付款方式先由 `transactions.py` 解析成帳戶，再傳給純 builder。
- **P2** `builder.check(form)` 只做表單語意；草稿層的不變條件全部在 `validation.py`；日期必填由 V05 負責。
- **P3** `services/transactions.py` 串接流程；router 只呼叫它。
- **P4** `TXN_STRUCTURE` 是依交易類型的第二道防線，只在其他錯誤都沒有時執行。
- **P5** 收入不使用付款方式，直接指定收款帳戶。
- **P6** V1 禁止從信用卡轉出（預借現金）；**P7** 信用卡繳款的扣款帳戶接受現金或銀行。
- **P8** 原幣欄位只開放支出的 MAIN 分錄。
- **P9** 收入分錄標 MAIN；轉帳、信用卡繳款不標 MAIN；手續費標 FEE。
- **P10** `Issue` 帶 `field`，讓介面可以把錯誤標在對應欄位。
- **P11** 預設付款方式由表單預先帶入；後端要求支出一定要收到 `payment_method_id`。
- **P12** 分期利息只能用在信用卡付款的消費。
- 轉帳轉入信用卡又有手續費 → `TXN_STRUCTURE`（field = fee_amount）；付款方式不存在 → V05、已停用 → V04；
  MANUAL 不受各類型結構限制，但受共同不變條件約束。

## Step 5：特殊交易（R1–R11）

- **R1** 期初以正常餘額方向輸入（資產 = 持有金額、負債 = 欠款），允許負數，0 元行略過；只接受資產、負債最末層。
- **R2** 一筆期初可以有多個帳戶；加總為 0 時不建立 0 元期初權益分錄。
- **R3** `OPENING_EXISTS`：同一筆內重複，或該帳戶已有有效期初 → 擋下；已刪除的期初不算。
- **R4** V10 不套用在 OPENING、PAYROLL。
- **R5** 調整差額不合法用 `ADJUSTMENT_DELTA`；V15：備註必填、只調整一個資產或負債帳戶、對方固定是帳務調整科目。
- **R6** 找不到系統科目 → `MissingSystemAccount`（系統異常，不是使用者輸入錯誤）。
- **R7** 薪資 = `txn_type PAYROLL` 的自由多分錄；固定欄位薪資單介面留到 V1.5。
- **R8** 薪資最低結構：至少一筆收入、收入必須是貸方、不能有權益分錄。
- **R9** 薪資的 line_role 選填；報稅彙總以科目的 tax_category 為準。
- **R10** `adjustment_total()`：帳務調整科目在 ADJUSTMENT 交易中加總的相反數；正數 = 帳戶餘額被調高。
- **R11** 期初日期不要求早於其他交易；未來日期走 V11。

## Step 6：生命週期與退款（U1–U14）

- **U1** 交易類型不能改（`TXN_TYPE_IMMUTABLE`）；已刪除的交易要先還原才能修改（`TXN_DELETED`）。
- **U2** D14 的分錄身分不含 memo，用 Counter 比對（重複分錄也正確）。
- **U3** V10 只在交易金額改變且超過門檻時確認；V11 只在日期改成未來時確認。
- **U4** 修改時 V13：新餘額 = 現在 − 舊影響 + 新影響，舊／新影響只在各自日期 ≤ 今天時計入。
- **U5** 刪除已刪除的 → `TXN_DELETED`；還原未刪除的 → `TXN_NOT_DELETED`；找不到 → `NotFound`。
- **U6** 還原檢查平衡、D12、退款規則、發票號碼（V08）；不重跑 V04、V10、V11。
- **U7** 退款方式可選；商家、`exclude_from_budget`、支出科目從原交易帶入。
- **U8** 已退金額 = 有效退款 MAIN 分錄加總；修改退款時排除自己。
- **U9** 新代碼：`REFUND_ORIGINAL`、`REFUND_DATE`、`REFUND_EXISTS`、`REFUND_LOCKED`、
  `TXN_TYPE_IMMUTABLE`、`TXN_DELETED`、`TXN_NOT_DELETED`。
- **U10** 原支出有退款時的鎖定（見 ADR-006）；不做同步更新退款。
- **U11** 退款不能改連到其他原交易。
- **U12** 退款不支援原幣；外幣超額退款用 MANUAL。
- **U13** 新增與修改共用 `transactions.py` 內部的草稿產生 helper，不重構 LedgerService。
- **U14** 還原期初允許引用已停用帳戶，但重新檢查 D12。
- 手寫退款草稿的 MAIN 科目和原交易不同 → `REFUND_ORIGINAL`，不另開代碼。
- 修改時把發票號碼改成已被使用的號碼，目前由資料庫部分唯一索引擋下並整批回滾；友善的 V08 在 P2。

## Step 7：收尾

- 架構守門補強：交易與 `deleted_at` 只在 LedgerService 異動；LedgerService 寫入只由 `transactions.py` 呼叫；
  查詢用的 `Transaction.status`／`deleted_at` 只在 `repositories/ledger.py`；router 不碰 repositories、
  LedgerService、Posting，也不自己 add／commit；repositories 不 commit、不 import services；
  T01–T14、T33、T34 都要有 `test_tXX_*` 測試。
- 金額欄位（`postings.amount`、`postings.original_amount_minor`、`credit_card_profiles.credit_limit`）
  必須是 INTEGER，由 schema 測試檢查；不對所有欄位全面禁止 Numeric。
- 不禁止其他地方在 `active_postings()` 上做 SUM（報表、預算會需要），守的是排除條件不能重寫。
- integrity 維持原本職責（不平衡、分錄不足、記在非最末層），不複製業務驗證（例如退款超額）。

## 延後與未來考量（尚未實作）

- **V08 完整版（P2）**：新增與修改時的發票號碼重複友善檢查。P1 只有資料庫索引與還原時的檢查。
- **V12 重複提醒（P2）**、**V14 預算提醒（P3）**、帳單週期與本期應繳（P3）、每日自動帳平檢查（P3）。
- **草稿交易（V1.5）**：P1 只建立 POSTED。`update`／`soft_delete`／`restore` 目前不檢查 `status`；
  V1.5 加入草稿時要決定是否新增 `TXN_NOT_POSTED`。
- **併發（已知限制）**：V07、D12 是先檢查再寫入，極端併發下理論上有 race。單一使用者 + SQLite + 日常記帳，
  P1／P2 不加入額外鎖定；出現實際需求再處理。
- 分期期數、薪資單固定欄位介面、科目搬移（V1.5 以後）。
