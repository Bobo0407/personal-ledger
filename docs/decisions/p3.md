# P3 上線：決策紀錄

P3 範圍：規格 F07、F20、F21、F26、F27、F29（首頁、預算、信用卡週期、月報、備份、部署）。
這份文件只記錄**已拍板、已實作**的決策；尚未拍板的事項不寫在這裡，也不代表現有行為。

## Step 切法

首頁採逐步加入區塊：每個 Step 只把自己已完成的功能放上首頁，不預留佔位。

| Step | 內容 |
|---|---|
| P3-1 | 首頁 I：帳戶餘額、帳平檢查警示 |
| P3-2A／2B | 信用卡週期 service；信用卡設定入口與首頁信用卡區塊 |

| P3-6 | 部署（repo 端完成；VM 驗收 pending） |
| P3-7 | 上線關卡 |

## P3-1：首頁帳戶餘額、帳平檢查警示

- **範圍**：首頁（`/`）在 P2 的兩個入口下方加入「帳戶餘額」與「系統狀態」兩區。沒有 migration（維持 0003），
  沒有新套件，不碰 LedgerService、EntryBuilder、`active_postings()`。信用卡本期應繳、預算、備份狀態留到各自的 Step。
- **分層**：`routers/home.py` 只驗證登入並呼叫 `services/home.home_summary()`；
  `repositories/accounts.list_shown_on_home()` 只查 `show_on_home = 1` 的科目（含停用），不判斷五大類。
- **哪些帳戶**：`show_on_home = 1` 且五大類為 ASSET／LIABILITY；其他五大類即使勾選也略過，不另外加驗證
  （規格 8.1 只定義資產、負債的算法）。順序 `(sort_order, code)`。
- **停用帳戶**：照樣顯示並標示「已停用」，金額是真實餘額（停用不代表沒有錢，隱藏等於藏錢）。
- **金額**：每列呼叫既有的 `ledger_queries.balance()`：`active_postings()`、截至今天（台北日期，不含未來交易）、
  含子孫科目、正常餘額方向（資產 +SUM、負債 −SUM）。首頁不另寫加總，也不重寫排除條件。
- **顯示**：負債餘額為正 → 「欠款 N」；為負 → 照實顯示負數，不加「欠款」（信用卡溢繳的完整語意留到 P3-2）。
  資產為負也照實顯示，不加顏色。判斷在 service（`HomeBalance.is_debt`），template 不判斷正負與科目類別。
- **不提供合計**：show_on_home 的科目可能有上下層關係，`balance()` 已包含子科目，逐列相加會重複計算。
  首頁沒有資產合計、淨資產（規格 8.1 首頁也沒有這些指標）。
- **帳平檢查**：見下一節。問題依交易合併成一列（同一筆交易的多個問題代碼合併顯示），
  連到 `/txn/{id}` 明細，已刪除、草稿另外標示。正常時只有一行小字「帳平檢查：正常」。
- **明細頁可以開啟損壞交易**：以測試確認不平衡、只有一筆分錄、沒有分錄、記在非末層科目、已刪除、草稿、
  不平衡的 EXPENSE，都能從警示連結進入 `/txn/{id}` 且回 200（`test_integrity_links_open_transaction_detail`）。
  沒有修改明細模組。

### 與規格 7.2 的差異：帳平檢查改為首頁即時執行（上線審查事項）

- **規格 7.2**：每天 03:30 由 APScheduler 呼叫 `integrity.check_all()`，有問題時在首頁顯示警示。
- **P3-1 實作**：每次開啟首頁時即時呼叫 `integrity.check_all()`；不加入 APScheduler，不新增資料表或設定值。
- **為什麼**：個人資料量小，每次全掃描的成本可以接受；結果永遠是最新的；V1 沒有其他排程工作需要 APScheduler
  （週期性草稿是 V1.5），只為帳平檢查引進排程器與儲存結果的資料表，成本高於效益。
- **差異與代價**：
  1. 沒有開首頁就不會檢查，也沒有「上次檢查時間」或歷史紀錄。
  2. 每次開首頁都掃描全部交易（含已刪除與草稿）；交易量大到首頁變慢時要重新評估。
  3. 檢查失敗（例外）時首頁回 500，不會靜默忽略。
- **上線審查待辦**：正式上線前確認「首頁即時檢查」是否可以取代「每日 03:30 排程」；
  V1.5 引進 APScheduler（週期性草稿）時，再決定是否改回排程並儲存結果。

## P3-2A：信用卡週期 service（F07、T18、規格 8.1）

- **範圍**：`services/credit_cards.py` 新增 `current_cycle()`、`amount_due()` 與純日期函式。
  沒有 migration，不改 router／template／首頁（P3-2B），不碰 LedgerService、EntryBuilder。
  沒有新增 repository 查詢：重用 `ledger_queries.balance()` 與 `ledger_repo.active_sum_for_accounts()`。
- **「本期」的意思**：`current_cycle` 表示「最近已結帳、目前等待繳款的 statement cycle」，
  不是正在累積中的下一期。結帳日之後新刷的消費屬於下一期，不計入本期應繳。
- **週期**：`statement_end` = 最近一個不晚於今天的結帳日；`statement_start` = 上一個結帳日 + 1 天。
  結帳日該月沒有該日時取月底（規格 6.2）。
- **結帳日當天的交易算本期（inclusive）**：依規格 8.1「最近一次結帳日當天的信用卡負債餘額」，
  與 `balance(as_of)` 含當天一致。不依銀行實際入帳日做特殊處理，差異列為已知限制。
- **繳款日**：`due_date` = 最近結帳日之後第一個符合 `due_day` 的日期；該月沒有該日則取月底；
  必須嚴格晚於 `statement_end`（`due_day` 等於結帳日，或月底截斷後等於結帳日時，落在下個月）。
- **公式**：
  `statement_balance = balance(卡, as_of=statement_end)`（欠款為正，含結帳日當天）；
  `paid_since = Σ CARD_PAYMENT 對該卡的分錄，txn_date ∈ [statement_end + 1, 今天]`；
  `raw = statement_balance − paid_since`；`amount_due = max(raw, 0)`；`overpaid = max(−raw, 0)`。
  全部走 `active_postings()`：已刪除、草稿不計入；未來日期的刷卡與繳款不計入。
- **只扣 CARD_PAYMENT**：依 V1 規格，本期應繳只從結帳日餘額扣除結帳日後的 `CARD_PAYMENT`；
  結帳日後的 `REFUND` 不對已結帳金額做跨期重算，因此不在 `paid_since` 中扣除。
  結帳日前的退款已反映在 `statement_balance`。`ADJUSTMENT`、`MANUAL` 同樣不當成繳款。
  這是系統內的計算規則，不代表銀行實際的入帳或退款政策。
- **溢繳**：兩個欄位 `amount_due` 與 `overpaid`，正負號判斷在 service，template 只顯示。
- **逾期**：`days_until_due = due_date − 今天`，已過期為負數；P3-2A 不新增 overdue flag，
  顯示文字留到 P3-2B。
- **邊界**：沒有信用卡設定 → 回傳 `None`（不推測週期）；非信用卡科目 → `RuleViolation("NOT_CREDIT_CARD")`；
  停用的信用卡仍可計算。
- **V1 分期全額入帳**：本金與利息在刷卡當天全額計入，有分期消費時本期應繳會偏高（規格 8.1）；
  不補償，V1.5 的分期追蹤才處理。有測試把這個行為釘住。

### 已知限制

1. **記帳日與銀行入帳日**：系統以交易日期認列，銀行帳單可能以入帳日切分，
   結帳日前後幾天的交易可能與帳單不同。
2. **結帳日沒有歷史版本**：之後修改信用卡設定，過去的週期會被重新切分（只影響顯示，不影響帳務）。
3. **分期偏高**：見上。
4. **上線首個週期的本期應繳可能不精準**：V1 首次上線時，如果信用卡只輸入一個「目前總欠款」的
   opening balance，而這個總欠款同時包含 (a) 最近一期已結帳、應繳的金額，與 (b) 結帳日之後尚未出帳的
   新消費，系統無法只靠單一 opening balance 自動還原這兩部分，所以本期應繳在第一個週期可能不精準
   （單一 opening 晚於最近結帳日 → 本期應繳偏低，且繳款後可能顯示溢繳；回填到結帳日 → 本期應繳偏高）。
   過了第一個結帳日之後，只要期間的繳款都有記，數字就恢復正確。
   - P3-2A **不**為此新增 schema、欄位或特殊計算。
   - **不可**把整筆目前總欠款簡單回填到最近結帳日，那會把結帳後的新消費也錯算成本期應繳。
   - 回歸測試 `test_opening_after_statement_end_is_not_in_statement_balance` 釘住這個行為：
     它記錄的是已知限制，不是要求 service 特判。
   - 這是 P3-7 的待辦，見下。

## P3-2B：信用卡設定入口、首頁信用卡區塊（F07、規格 7.3、8.1）

沒有 migration，不碰 LedgerService、EntryBuilder，不改 P3-2A 的日期與 `amount_due` 邏輯。

- **設定入口**：`GET /settings`（規格 7.3），目前只有「信用卡設定」，不做 settings framework。
  列出所有啟用中的信用卡，不論 `show_on_home`；每張卡一個表單，普通 POST + 303，不用 HTMX
  （三個欄位、很少修改）。成功後轉回 `/settings?saved=<id>` 顯示「已儲存」；
  失敗回 422，輸入保留，錯誤顯示在該卡表單內（M07 同一個代碼涵蓋日期與扣繳帳戶，不拆欄位）。
- **欄位**：結帳日、繳款日（1–31，必填）、扣繳帳戶（可不設定）。驗證全在 `set_profile()`；
  router 只把文字轉成整數（空白 → None、非整數 → 0，兩者都由 `check_day` 擋下）。
- **credit_limit**：V1 schema 的選填欄位；F07／P3-2B 沒有它的 UI。`set_profile()` 沒收到額度會清成
  None，所以設定頁走 `update_card_settings()`：先讀出既有額度再原封不動傳回 `set_profile()`，
  表單送來的 `credit_limit` 一律忽略。`set_profile()` 本身未改。
- **扣繳帳戶選項**：啟用中、末層的 ASSET／BANK（repository 查詢，與 M07 同條件；最終仍以 service 驗證）。
- **首頁區塊**：只顯示 `show_on_home = 1` 的 CREDIT_CARD。啟用卡無設定 → 「尚未設定結帳日」＋前往設定；
  停用卡有設定 → 顯示並標「已停用」；停用卡無設定 → 略過；沒有符合的卡 → 整個區塊不出現。
  數字全部來自 `credit_cards.amount_due()`，template 不計算日期或金額。
  不做 `show_on_home` 的編輯 UI。首頁導覽列加「設定」入口。
- **顯示語意**：`amount_due > 0` → 本期應繳、繳款日、還有 N 天（0 天顯示「今天截止」）；
  `amount_due = 0` → 只顯示繳款日，不顯示剩餘天數（對規格 8.1 的小幅收斂）；
  `overpaid > 0` → 另顯示「已多繳 N」。
- **逾期文字**：`days_until_due < 0` 且 `amount_due > 0` 時顯示
  「依目前記帳資料，繳款日已過 N 天，尚有 N 元本期應繳。」只是顯示判斷（`HomeCard.is_overdue`），
  沒有新增 overdue 旗標。只出現在「繳款日之後、下一個結帳日之前」：過了下一個結帳日，未繳金額會併入
  新一期的結帳日餘額，提示隨之消失，金額仍計入本期應繳。
- **已知限制提示**：首頁區塊固定一行「金額依記帳資料推算，可能與銀行帳單不同（入帳日、分期、首期期初餘額）。」；
  設定頁提醒「修改後，過去的週期會重新切分，只影響顯示，不改帳務」。

## P3-3A：預算 schema 與 service（F20、F21、M05、T15–T17、規格 6.9、8.1）

只有 schema 與 service：沒有 `/budgets` 頁、沒有首頁預算區塊、V14 沒有接線。
不碰 LedgerService、EntryBuilder。

- **schema（migration 0004）**：`budgets(id, account_id FK, monthly_amount > 0, effective_from 'YYYY-MM',
  created_at, updated_at)`，`UNIQUE (account_id, effective_from)`；月份格式有 CHECK（GLOB 加月份 01–12）。
  不儲存已用金額、使用率或任何合計；FK 不 cascade；不加額外索引（UNIQUE 已涵蓋依科目查）。
  downgrade 只刪 `budgets`。seed 不含預算。
- **M05**：`services/budgets.set_budget()` 檢查「EXPENSE 且 parent_id 為空」。沒有子科目的第一層費用科目也允許。
  停用的科目不能新設預算。目前沒有「搬移科目」功能；日後若加，必須檢查 budgets，否則會破壞 M05。
  `delete_account()` 新增 `BUDGET_ACCOUNT` 檢查，避免 FK 錯誤變成 500。
- **已用（used）**：指定月份的**整個 calendar month**（月初到月底，含頭尾），第一層費用科目與所有子孫科目的
  有效分錄加總。有效 = `active_postings()`（POSTED 且未刪除；DRAFT 與已刪除排除）。
  - **沒有「截至今天」的截止**：POSTED 但日期在未來、且落在該月的交易，照樣計入該月。
    （與帳戶餘額、V13 的「截至今天」慣例不同，這是刻意的：預算看的是「該月的支出」。
    若日後需要區分「截至今日已花」與「本月已排定支出」，那是新需求。）
  - **不依 txn_type 篩選**：手續費、利息、薪資扣款、MANUAL 的費用分錄，只要實際落在該科目底下就計入。
  - **排除 `exclude_from_budget = 1`**：整筆交易（含它的手續費與利息分錄）。
    實作是 `active_sum_for_accounts(..., budget_only=True)`，其他呼叫端的預設行為不變。
    月報的支出仍然包含這些交易（T16）。
  - **退款**：貸記原費用科目，依分錄正負號自然沖減；退款繼承原交易的 `exclude_from_budget`。
    `used` 可以是負數（例如下個月才退款），不 clamp；`remaining = budget − used`，可以大於預算。
- **生效版本**：指定月份採用同科目 `effective_from ≤ 該月` 的最新一筆；比第一筆還早的月份沒有預算。
  同科目同月份已有版本時原地更新金額，否則新增一筆（不去除重複金額的版本）。
- **V1 產品限制：`effective_from` 不得早於目前月份。** 這是為了避免歷史月報被事後改寫而新增的限制，
  **不是原 schema 明文要求，也不是資料庫限制**（DB 不擋過去的月份）。
  未來若有「補錄歷史預算」的需求，另行評估。
- **V1 不支援取消預算**：沒有結束月（不新增 `ended_from`）、不用 0 表示取消、不提供 `delete_budget`。
  是否允許刪除「尚未生效的未來版本」，留到 P3-3B 真正有 UI 需求時再決定。
- **停用科目**：該月有生效預算就照樣列出（`is_active = False`），不因停用而讓預算消失。
- **使用率與狀態**：`usage_pct = floor(max(used, 0) × 100 / budget)`；`used < 0` 時顯示 0、狀態 OK。
  狀態用整數交叉乘法判斷，不用四捨五入後的百分比：`used ≥ budget` → OVER（100% 固定）；
  `used × 100 ≥ alert_pct × budget` → WARN；否則 OK。
- **`budget_alert_pct`**：讀 settings，不存在預設 80；有效範圍 1–99；存在但不合法 → `InvalidSetting`（不靜默改用預設）。
  `InvalidSetting` 搬到 `services/errors.py`（`validation.py` re-export，既有匯入不變），
  避免 P3-3C 讓 `validation.py` 匯入 `budgets.py` 時循環匯入。
- **V14（P3-3A 只做純函式）**：`crossing(before, after, budget, alert_pct)`：
  變動前 `< T%` 且變動後 `≥ T%`（剛好到達也算）；同時跨過兩個門檻只回報較高的；
  已經高於門檻後再增加、用量減少都不算。草稿差額、create／edit／restore 接線與 `PostResult.notices`
  留 P3-3C，屆時掛在 `validate()` 與 `validate_restore()` 的 notices（與 V13 同位置）。
- **不寫稽核紀錄**：預算屬於主資料，與信用卡設定一致。

## P3-3B：預算設定頁與首頁預算區塊

範圍：`/budgets` 設定頁、首頁「本月預算」區塊、共用的 `partials/budget_card.html`。不新增 migration，不改 LedgerService／EntryBuilder，不做 V14 接線（留 P3-3C）。

- **路由**：`GET /budgets`、`POST /budgets/{account_id}`；普通 POST + 303（`?saved=<id>`），驗證失敗回 422 整頁並保留輸入；不用 HTMX。
- **列出的科目**：啟用中的第一層費用科目（M05）；已停用但本月有有效預算者唯讀顯示，不提供表單。
- **生效月份**：`<input type="month">`，預設本月、`min` = 本月。`min` 只是瀏覽器提示；真正的檢查在 `set_budget()`，竄改成過去月份仍回 422（`BUDGET_PAST_MONTH`）。template 不判斷預算語意。
- **版本顯示**：「本月生效」的版本加上「已排定」的未來版本（`budget_repo.later_versions()`，唯一新增的 repository 查詢）。V1 不提供取消／刪除預算，所以排定的版本只能用同月份覆寫金額。
- **狀態呈現**：`BudgetCard.state`（ok／warn／used_up／over）由 service 決定；畫面只選文字與樣式，用既有 `--warn-*`／`--danger-*` token，不做進度條。used < 0 時保留負值、使用率顯示 0%。
- **首頁**：帳戶餘額之後、信用卡之前；列出所有本月有效預算，不排序、不截斷；無預算時顯示「尚未設定預算」＋「前往設定」。
- **已知後果**：V1 不能取消預算，因此科目停用後，只要仍有有效預算，首頁仍會顯示並標「已停用」。已接受。
- **`budget_alert_pct` 異常**：不 fallback 成 80。首頁預算區塊與 `/budgets` 的進度顯示 banner 錯誤；首頁其他區塊與 `/budgets` 設定表單仍可使用。
- **未做**：月報、備份、年度預算、累積結餘、圖表、通用 dashboard／form 框架。375px 版面不作 blocking，留 P3-7 實機檢查。

## P3-3C：V14 預算跨門檻提醒、儲存後預算卡片、一次性提醒（F21、V14、規格 9.1）

不新增 migration，不改 EntryBuilder。LedgerService 只有一處小改（見「刪除」）。

**觸發語意**
- 預算 key = （第一層費用科目, `txn_date` 所在月份）；用該月自己的生效版本（含已排定的未來版本），沒有 today 截止。
- contribution = 該交易落在該第一層科目子樹的分錄淨額；不依 txn_type，`exclude_from_budget` 的交易沒有 contribution。
- before = 寫入前 DB 的 used；after = before − 舊 contribution + 新 contribution。新增（舊=無）、修改（舊→新）、還原（舊=無，已刪除的不在 used 裡）、刪除（新=無）。
- 跨過 80%：`before×100 < alert_pct×budget ≤ after×100`；跨過 100%：`before < budget ≤ after`（剛好用完也算）。同時跨兩個只報 100；已高於門檻再增加不報。沿用 P3-3A 的 `crossing()`，validation.py 不重寫 threshold。
- 沒有提醒歷史：每次用 DB 現況重算，所以「改低再改高」會再報一次。
- delta ≤ 0（用量沒增加）不可能跨過，直接略過；因此 refund、減少金額、exclude 變 true 都不寫特例就不會提醒。修改退款讓退款變少、刪除退款，都是用量上升，依同一公式可能跨過。
- 一筆交易可影響多個第一層預算，各出一則 V14。排序：100% 在前，其次依科目順序（`sort_order`、`code`），最後依月份。同一個第一層科目底下的多筆分錄先淨額。

**接線**：`validate()`／`validate_restore()`／新增的 `validate_delete()` 各呼叫一次 `validation.budget_notices()`，結果經既有 `PostResult.notices` 流出；code 一律 `V14`，靠文字區分 80% 與 100%。月份不是目前月份時科目名後面標示月份。

**設定異常**：`budget_alert_pct` 不合法時不 fallback 成 80、不阻擋儲存，整筆交易只回一則 `BUDGET_ALERT_CONFIG`（不冒充 V14）。只有在「用量增加且該月有生效預算」時才讀設定，沒設預算的人永遠不受影響。文字：「預算提醒設定異常，這筆交易已儲存，但無法判斷是否跨過預算門檻。」；刪除時「已儲存」改成「已刪除」。

**刪除（D7 impact audit）**：`soft_delete()` 只有一個 caller（`transactions.delete_transaction()` → `POST /txn/{id}/delete`），測試都忽略回傳值。改成回傳 `PostResult`（notices 只有 V14／設定異常），不改其他 lifecycle API，所以納入 P3-3C，不列為已知限制。

**儲存後預算卡片**：`budgets.cards_for_transaction()` 在儲存後讀交易，回傳它「目前」計入的預算（edit 之前的舊 key 不顯示；exclude 的交易沒有卡片），重用 `partials/budget_card.html`；卡片月份不是目前月份時（`BudgetCard.month_label`）標示月份。顯示於：新增後（兩種表單分支）、修改、還原、退款後的明細頁。template 不計算任何數字。

**一次性提醒（D6）**：「儲存並回首頁」與「刪除」成功後都會離開頁面，提醒不能消失。repo 沒有 session／flash，所以仿 `entry_run.py` 新增 `app/flash.py`：簽章 cookie `ledger_flash`（Path=/，HMAC 前綴 `flash:`，5 分鐘過期，最多 5 則，編碼後 ≤ 3,000 字元）。成功回應 Set-Cookie，`GET /`（儲存並回首頁）與 `GET /txn/{id}`（刪除）讀完同一個回應就刪除，重新整理不會重複。V13 與 V14 走同一條路。`ledger_run` 是不同的 cookie（Path=/txn）：不讀、不寫、不清除；「儲存並記下一筆」不使用 flash。

**已知限制**：新增的 flash 只涵蓋這兩條離開頁面的路；沒有通用通知框架。edit 時被移走的舊 key（換月份、換科目）不顯示卡片。

## P3-4：月報（規格 8.2、T16、7.3）

`GET /reports/monthly?month=YYYY-MM`，登入後可用，首頁導覽新增「月報」。只讀：不新增 migration、
repository 查詢、彙總表、快照或快取；不改 LedgerService／EntryBuilder。所有數字在 `services/reports.py`
即時計算，router 與 template 不做帳務運算。V1 沒有圖表、匯出、年度報表（`/reports/yearly` 是 V1.5）。

**月份參數**
- 預設目前月份；過去與未來月份都可以看（未來日期的 POSTED 交易本來就能存在）；`month=` 空白視同預設。
- 只驗證格式：`YYYY-MM`、年份 4 位數、月份 01–12（沿用 `budgets.month_range()` 的契約）。
  **沒有** 2000–2099 之類的產品限制。`date` 本身撐不住的邊界（0000 年、9999-12、月初前一天不存在的
  0001-01）當成無效月份，同樣回 422，不會 500。
- 無效月份回 422 完整頁（錯誤碼 `REPORT_MONTH`，保留月份選擇器與「回到本月」），不靜默改成本月。

**收入與支出：依科目大類，不依交易類型**
- 收入 = `abs(class_total(INCOME))`。**這是依目前 v1.0 規格字面實作**（規格 8.2：「收入科目分錄加總的絕對值」）。
  一般月份與 `class_total` 的正方向結果相同；收入被沖銷成淨負值的月份仍顯示絕對值。
  若未來希望收入沖銷月份保留負號，必須先正式修改報表規格，不在 P3-4 偷改。
- 支出 = `class_total(EXPENSE)`：含 `exclude_from_budget = 1`（「不計入預算」只影響預算進度，T16）；
  退款貸記費用科目、自然沖減，可以是負數，不 clamp；手續費、利息、薪資扣款、手動分錄只要落在費用科目就計入。
  轉帳、繳卡費只碰資產／負債，期初與帳務調整的對方是權益科目，所以天然不混入收入或支出。
- 結餘 = 收入 − 支出。儲蓄率 = 結餘 ÷ 收入，一位小數、half up（`Decimal`）；收入 ≤ 0 → `None`，畫面顯示
  「—（本月沒有收入）」；結餘為負時允許負儲蓄率；不顯示「-0.0%」。service 回 raw `Decimal`。
- 帳務調整合計（規格 8.2 V1 項目）重用 `adjustment_total()`。

**各科目支出與預算對照（T16 同時成立）**
- 第一層費用科目：`actual = period_total`（含子孫、含不計入預算的交易）；預算進度重用
  `budgets.budget_cards()`（排除不計入預算的交易）。兩者來自同一批有效分錄，只差 `budget_only`。
- `excluded_amount = actual − budget.used`，**保留正負號**：不計入預算的支出 → 正，不計入預算交易的退款 → 負
  （例：9 月不計入預算的支出 1,000，10 月退 300 → 10 月 actual −300、已用 0、差額 −300）。
  差額為 0 不顯示；不為 0 顯示「不計入預算淨額 +30,000／-300 元（實際支出 − 預算已用）」。沒有預算 → 0。
- 列出規則：有預算、或實際不為 0 才列；實際為 0 又沒有預算省略；停用科目同樣適用並標「已停用」。
- 第二層只列直接 child（金額已含更深的子孫，第三層折進第二層，沒有通用樹狀報表）；金額為 0 的 child 不列。
  第一層自己直接記帳的部分（LedgerService 只允許末層記帳，正常為 0）非 0 時列「直接記在此科目」，
  讓各項加總永遠等於第一層合計。
- `budget_alert_pct` 不合法：只有預算欄顯示錯誤（不 fallback 成 80），支出金額與其他區塊照常。

**帳戶與淨資產**
- 列出所有資產、負債的**末層**科目（不限 `show_on_home`，父科目的餘額含子孫，列出來會重複）。
  啟用帳戶一律列；停用帳戶月初或月底不為 0 才列。負債維持正常方向，正數顯示「欠款 N」。
- 月初 = 月初前一天的 `balance(as_of)`；月底 = 月底的 `balance(as_of)`。淨資產直接呼叫 `net_worth(as_of)`，
  不是把列加起來。權益科目（期初權益、帳務調整）是分錄的對方，不直接進淨資產。

**日期語意**
- 指定月份的整個 calendar month（含頭尾），沒有 today 截止，與預算（P3-3A）同一個月界；
  deleted／DRAFT 一律由 `active_postings()` 排除，report service 不重寫 `deleted_at`／`status`。
- 與首頁的差別：首頁餘額是「截至今天」，月報月底餘額是「截至月底」。看目前或未來月份時，月底餘額
  會包含該月稍後日期的 POSTED 交易，畫面註明「月底餘額包含本月稍後日期的交易」。

**已知例外：淨資產恆等式**
- 規格 8.2 的「淨資產變化 = 本月結餘 + 帳務調整合計」在**本月有 OPENING 交易**時不成立（期初餘額也會讓淨資產
  上升）。畫面不宣稱這個恆等式，只分別顯示月初／月底淨資產與帳務調整合計；測試驗證沒有 OPENING 的月份成立，
  並用一個測試記錄 OPENING 月份的差額（= 期初金額）。

**查詢量**：逐科目重用既有查詢（約「第一層數 + 第二層數 + 帳戶數 × 2」次小查詢），單人 SQLite 足夠；
日後若覺得慢，再換成單次分組查詢，語意不變。

## P3-5A：本機加密備份、backup_runs、首頁備份狀態（F29、規格 7.2、8.1）

只做本機。不做 Google Drive／rclone／OAuth／遠端清理（P3-5B）、不做 systemd unit／timer（P3-6）、
不做 APScheduler 或 job framework。不改 LedgerService／EntryBuilder／帳務 schema。
migration 0005 只建立 `backup_runs`；downgrade 只刪這張表（紀錄遺失，備份檔與帳務資料不受影響）。

**流程與安全**
- SQLite backup API（來源用唯讀 URI 開啟，不可能被改動，也不會被建立）→ 記憶體快照做 `PRAGMA integrity_check`
  → `serialize()` → `gzip` → `age -r <公鑰>` 輸出到 `.part` → `os.replace` 成正式檔名。
  **磁碟上不會出現未加密的 DB 或壓縮檔**；`finally` 只需清掉 `.part`（密文）。代價是記憶體約為 DB 大小的 2–3 倍。
- 只用 age **公鑰**（`BACKUP_AGE_RECIPIENT`）；私鑰不在伺服器，只有還原驗證時用 `--identity` 傳入。
  recipient、identity 的內容與路徑不寫進 log、`backup_runs.error` 或畫面；錯誤訊息中的 recipient 與
  `AGE-SECRET-KEY-…` 一律遮蔽；格式不對的 recipient 不回顯（可能誤貼私鑰）。
- 備份程序不需要 `SECRET_KEY`（`BackupSettings` 繼承 `DatabaseSettings`）。設定：`BACKUP_DIR`（預設 `./data/backups`）、
  `BACKUP_AGE_RECIPIENT`（必填）、`BACKUP_AGE_BIN`（可覆寫）。
- 偏離規格：以 `scripts/backup.py` 取代 `scripts/backup.sh`（Windows 開發機與 CI 都能直接跑與測）。
  加密選型見 ADR-008。
- 檔名 `ledger-YYYYMMDD-HHMMSS.db.gz.age`（台北時間，不含版本與個資）；同一秒重名加 `-2`、`-3`。

**backup_runs（只在結束時寫一筆）**
- 欄位：規格 §6 的 `started_at`、`finished_at`、`status`、`file_name`、`size_bytes`、`error`，加上專案慣例的
  `created_at`／`updated_at`。status 只有 `SUCCESS`／`FAILED`，**沒有 RUNNING**（強制中斷不會留下卡住的紀錄，
  「超過 36 小時沒備份」警示本來就涵蓋）。CHECK：SUCCESS 必須有 `file_name`、`size_bytes ≥ 0`；FAILED 必須有 `error`。
- **FAILED 紀錄的保證範圍（刻意寫準確）**
  - 來源 DB 仍可寫、備份 pipeline 失敗：嘗試寫一筆 FAILED，然後以 exit 1 結束。
  - 來源 DB 不存在／嚴重損毀／無法寫入，或 `backup_runs` 的 INSERT 本身失敗：**無法保證有 FAILED 紀錄**。
    `logger.exception` ＋ exit 2；不建立第二個 metadata DB 或額外監控系統。若備份檔已完整產生會保留。
  - 首頁只能反映 DB 裡實際存在的 `backup_runs`；DB 本身壞掉時，網站沒有義務靠它自救（最多 36 小時後，
    沒有新的成功紀錄會讓首頁出現警示——前提是網站和 DB 還活著）。
- 檔案操作全在 DB transaction 之外；DB 只有結束時一個單句 INSERT＋commit。

**保留（規格 F29）**：每日備份 30 天，加上每月第一份 12 個月（定義為當月與前 11 個月；「第一份」是該月目前存在的最早一份）。
只刪除檔名完全符合格式的檔案，永遠不刪剛產生的那份。
- **清理失敗不讓備份失敗，但不能靜默**：備份檔成功＋清理失敗 → `status = SUCCESS`、`error` 存固定的簡短警告、exit 0；
  `backup_status()` 回 warn，首頁黃色「最後備份成功，但舊備份清理失敗，請檢查 log」（不顯示 error 原文或路徑）。
  下一次備份與清理都成功後自然恢復 ok。沒有新增 WARNING status 或 schema。

**首頁備份狀態**（`backup.backup_status()`，template 只印）：FAILED → 紅色 alert；SUCCESS 超過 36 小時（嚴格大於）→ 黃色；
SUCCESS 但清理失敗 → 黃色；沒有任何紀錄 → 黃色；其餘一行小字「最後備份：今天 03:00 ✓」。
FAILED 不顯示 error 原文（避免路徑與命令輸出進 HTML），細節在 log。只看最後一筆。時間格式沿用專案慣例
（台北時區 ISO 8601 字串），36 小時用帶時區的 datetime 相減，與 DST 無關。

**還原驗證（restore smoke test）**：`scripts/restore_check.py` 解密 → gunzip → 以記憶體 SQLite 開啟 →
`integrity_check` → 顯示 alembic 版本與表筆數；明文只在記憶體，不寫入磁碟。自動化測試涵蓋
「備份 → 解密 → SQLite 可讀、與來源一致」的往返（用真的 age）。**P3-7 launch gate 仍要人工做**：
下載最新備份 → 解密 → Docker 啟動 → 各帳戶餘額與正式環境一致。CI 安裝真的 age；CI 缺 age 時測試失敗，不 skip。

**P3-5B 必須重新 audit**：P3-5A 的 `SUCCESS` 只代表「本機加密備份完成」。加上傳之後 SUCCESS 的正式語意
已在 P3-5B 決定（見下一節與 ADR-009）。

## P3-5B：雲端上傳（rclone）、遠端保留、遠端還原驗證（F29、規格 7.2）

不做 systemd timer／部署（P3-6）、Docker 還原與真實餘額核對（P3-7）。不引入 Google Drive Python SDK、
不做多雲抽象、不做 queue／worker、不做 `upload_events`、不新增 migration（Alembic 仍是 0005）。
不改 LedgerService／EntryBuilder／帳務 schema。選型與取捨見 ADR-009。

**流程（順序固定）**：SQLite backup → gzip → age → 本機密文 → `rclone copy --immutable --include /<檔名>`
→ `rclone lsjson` 驗證 → 本機清理 → 遠端清理 → 寫一筆 `backup_runs`。只有 age 密文會被上傳。

**設定**：`RCLONE_REMOTE`（rclone 的 remote 名稱）、`RCLONE_PATH`（預設 `ledger-backups`）、`RCLONE_BIN`、
`RCLONE_CONFIG`（選填，rclone.conf 路徑，以 `--config` 傳入）。沿用 `BACKUP_DIR`。`rclone.conf` 含 OAuth token，
視為 secret，不進 Git（`.gitignore` 已涵蓋）。remote 名稱與路徑做格式檢查，不回顯設定值。

**上傳成功的判定（我們自己的契約）**：rclone exit 0，且 `lsjson` 找得到該檔名、遠端大小等於本機大小。
不依賴 Drive 的 MD5 或任何 backend 的 hash 行為；rclone 內部若另有驗證只是額外保障。

**SUCCESS／FAILED 語意**

| 情境 | status | file_name | error | exit | 首頁 |
|---|---|---|---|---|---|
| 本機＋雲端都完成、清理正常 | SUCCESS | ✓ | NULL | 0 | 一行小字 ✓ |
| 完成，但本機或雲端清理失敗 | SUCCESS | ✓ | 固定清理警告 | 0 | 黃色「…舊備份清理失敗，請檢查 log」 |
| `--local-only`（明確指定） | SUCCESS | ✓ | 固定「僅本機」警告 | 0 | 黃色「最後備份僅在本機，尚未上傳雲端」 |
| 本機密文完成，雲端上傳／驗證失敗 | **FAILED** | ✓（保留） | 固定「雲端上傳失敗」 | 1 | **紅色**「本機備份已完成，但雲端上傳失敗…」 |
| 沒設 `RCLONE_REMOTE` 且沒有 `--local-only` | FAILED | NULL | 設定錯誤說明 | 1 | 紅色（一般失敗文字） |
| 本機 pipeline 失敗 | FAILED | NULL | 簡短錯誤 | 1 | 紅色 |
| 來源 DB 不存在／INSERT 失敗 | 不保證有 row | | | 2 | 看 DB 內實際 row |

- 「本機有救命檔」靠 `file_name` 是否為 NULL 這個結構性訊號區分，不靠字串判斷；template 不做判斷，
  全部由 `backup_status()` 決定。raw rclone stderr、token、設定檔內容不進 `backup_runs`、log（先遮蔽並截斷）或 HTML。
- 上傳失敗時：本機檔保留、**不做任何清理**（降級時不動舊備份）、exit 1，下一次完整成功後首頁恢復 ok。
- 清理失敗不影響這次上傳成功（SUCCESS＋固定警告）；本機與遠端各自有固定警告字串，首頁用同一句。
- **歷史**：P3-5B 之前寫入的 SUCCESS 一律視為「僅本機」。正式環境的第一次排程備份在 P3-6，晚於 P3-5B，
  所以正式資料庫沒有這種歷史；只可能存在開發複本，不需要 schema 來區分。
- **`--local-only` 是明確 opt-in**（開發／CI）。**P3-6 的正式排程不得使用**。忘了設定 Google Drive 的正式環境會得到
  FAILED 與紅色警示，而不是看起來正常的 SUCCESS。

**遠端保留**：規則與本機完全相同（每日 30 天＋每月第一份 12 個月），重用 `select_deletions()`；以檔名時間戳為準，
不看遠端修改時間；只處理合法備份檔名，只用 `deletefile` 單檔刪除，不用 `sync`／`purge`／`delete`；
遠端資料夾內其他檔案與子資料夾永遠不碰；剛上傳的檔案受保護；listing 失敗就整段不刪（它同時是上傳驗證的一部分）。
`backup_remote.delete()` 自己再檢查一次檔名格式，非備份檔名一律拒絕、不會呼叫 rclone。

**重複與重試（最小策略）**：每次執行都會產生新的時間戳本機檔；不做 `--upload-only`、不補傳舊檔、不做預先列表。
遠端已有同名但不同的檔案 → rclone 失敗 → 記為上傳失敗，不覆蓋、不猜內容是否相同。
**實測發現**：rclone 1.75.2 的 `copyto --immutable`（單檔模式）不會擋覆蓋（exit 0），所以上傳改用目錄模式的
`copy --immutable --include`（會失敗，exit 6）。Drive 上的實際行為待 Windows 真 Drive 驗收確認，不寫成已保證。

**還原驗證**：`scripts/restore_check.py --remote latest|<檔名> --identity <私鑰檔>`：下載密文到暫存目錄（結束就刪）→
age 解密 → gunzip → 記憶體 SQLite → `integrity_check`、`alembic_version`、主要表筆數。`latest` 只從合法備份檔名中選最新，
其他檔案一律忽略；不合法或不存在的檔名拒絕。不覆寫任何正式資料庫。
- **分工**：P3-5B 只驗「下載＋解密＋SQLite 可讀」；P3-6 做正式主機的 rclone／timer／部署接線；
  P3-7 才做「下載最新正式備份 → 還原 → 啟動 app／Docker → 真實帳戶餘額核對」。

**測試與 CI**：真 age＋真 rclone（local backend 當「雲端」，暫存 `rclone.conf`），不放任何 Google token；
失敗注入與 token 不外洩用 mock 的 subprocess。CI 安裝真的 rclone；CI 缺 rclone 時測試失敗，不 skip。
**Google Drive 專屬行為只能靠 Windows 真 Drive 驗收確認**（`drive.file` scope 的可見範圍、Drive 垃圾桶行為、
hash 驗證等），文件只列為建議，不宣稱已驗證。

## P3-6：部署（規格 4.2、7.2）

**狀態：repo 端 implementation complete；真 Linux VM 驗收 pending（不得標 CLOSED）。** 驗收順序與紀錄表見
`docs/deploy.md`；取捨見 ADR-010。不改 `app/`、LedgerService、EntryBuilder、帳務 schema，不新增 migration。

**新增**：`deploy/ledger.service`、`deploy/ledger-backup.service`、`deploy/ledger-backup.timer`、`deploy/Caddyfile`
（網域是 placeholder `YOUR_DOMAIN_HERE`，VM 上複製後才替換）、`deploy/ledger.env.example`（只有 placeholder 或空值）、
`docs/deploy.md`、`docs/adr/ADR-010-deployment.md`、`tests/unit/test_deploy_files.py`（靜態守門測試）。

**決定**
- 單台 Ubuntu 24.04 VM、Python 3.12 venv、不用 Docker／K8s。`/srv/ledger/{app,venv,config,data,logs}`；
  網站與備份用同一個非 root 的 `ledger` 使用者。
- 權限：兩個 service 都 `UMask=0077`，runbook 的互動指令用 `umask 077`（`lrun`）；`config/`、`data/`、`logs/` 為 0700，
  `ledger.db`、`ledger.env`、`rclone.conf`、備份檔為 0600；驗收用 `stat` 與 `find -perm /077` 確認。不使用 ACL。
  （相對於計畫的小調整：`data/`、`logs/` 由 0750 改為 0700，讓「沒有 group／other 權限」可以用單一指令驗證。）
- Uvicorn 單 worker，只 bind `127.0.0.1:8000`；Caddy 反向代理並自動 HTTPS；只開 22／80／443。
- migration 只在部署流程手動執行（app 停止後），不放 `ExecStartPre`。有 migration 時：先確認最近一次完整遠端備份 SUCCESS →
  停止 app 並確認已停止 → **只在 app 已停止後**複製 SQLite 檔案到 `data/pre-deploy/`（0600）→ migration → `alembic current`
  為 head → 啟動。失敗就不啟動、不自動 downgrade，rollback 優先 fix-forward，必要時人工還原快照。
- 備份 timer：每日 03:00 `Asia/Taipei`、`Persistent=true`；`ExecStart` 直接呼叫 `scripts/backup.py`，不得使用本機專用旗標。
  exit 1／2 使 unit failed。
- **03:30 integrity job 不部署**：沿用 P3-1 的「每次開啟首頁即時檢查」決策（見上文 P3-1 節），不新增 scheduler。
- 不新增 `/health`（`GET /login` ＋ `alembic current` ＋ 人工登入）；不做 `deploy.sh`；GitHub Actions 維持 lint／test，
  不做自動 deploy 或 production secrets。
- Google OAuth：自建 Desktop client、scope `drive.file`；共用 client_id 不得進 production。`rclone.conf` 優先在有瀏覽器的機器用
  `rclone config` 產生再安全複製到 VM（Windows 驗收版本 v1.75.1，正式環境對齊該版本）。
  runbook 只保留實際跑通的方法，**不寫未實測的 rclone 指令**；Console 發布狀態與 token 行為待實際確認，
  並要有 §10-J 的延後檢查（發布後 8 天以上仍可上傳）。
- 偏離規格：`scripts/backup.sh`／`restore.sh` 以 `scripts/backup.py`／`restore_check.py` 取代（見 P3-5A）；
  規格的 Dockerfile／docker-compose 是 Demo 用，不屬於 production。

**P3-6 仍待真 VM 驗收**：systemd app、Caddy HTTPS、DNS、8000 不對外、migration current=head、資料持久、自建 OAuth client、
backup service／timer、遠端備份、重開機恢復、權限（stat）、journal／logging。
