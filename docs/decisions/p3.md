## P3-1：首頁帳戶餘額、帳平檢查警示

- **範圍**：首頁（`/`）在 P2 的兩個入口下方加入「帳戶餘額」與「系統狀態」兩區。沒有 migration（維持 0003），
  沒有新套件，不碰 LedgerService、EntryBuilder、`active_postings()`。信用卡本期應繳、預算、備份狀態留到各自的 Step。
- **分層**：`routers/home.py` 只驗證登入並呼叫 `services/home.home_summary()`；
  `repositories/accounts.list_shown_on_home()` 只查 `show_on_home = 1` 的科目（含停用），不判斷五大類。
- **哪些帳戶**：`show_on_home = 1` 且五大類為 ASSET／LIABILITY；其他五大類即使勾選也略過，不另外加驗證
  （規格 8.1 只定義資產、負債的算法）。順序 `(sort_order, code)`。
- **停用帳戶**：照樣顯示並標示「已停用」，金額是真實餘額（停用不代表沒有錢，隱藏等於藏錢）。
- **金額**：每列呼叫既有的 `ledger_queries.balance()`：`active_postings()`、截至今天（台北日期，不含未來交易）、
  含子孫科目、正常餘額方向（資產 +SUM、負債 −SUM）。首頁不另寫加總，也不重寫排除條件。
- **顯示**：負債餘額為正 → 「欠款 N」；為負 → 照實顯示負數，不加「欠款」（信用卡溢繳的完整語意留到 P3-2）。
  資產為負也照實顯示，不加顏色。判斷在 service（`HomeBalance.is_debt`），template 不判斷正負與科目類別。
- **不提供合計**：show_on_home 的科目可能有上下層關係，`balance()` 已包含子科目，逐列相加會重複計算。
  首頁沒有資產合計、淨資產（規格 8.1 首頁也沒有這些指標）。
- **帳平檢查**：見下一節。問題依交易合併成一列（同一筆交易的多個問題代碼合併顯示），
  連到 `/txn/{id}` 明細，已刪除、草稿另外標示。正常時只有一行小字「帳平檢查：正常」。
- **明細頁可以開啟損壞交易**：以測試確認不平衡、只有一筆分錄、沒有分錄、記在非末層科目、已刪除、草稿、
  不平衡的 EXPENSE，都能從警示連結進入 `/txn/{id}` 且回 200（`test_integrity_links_open_transaction_detail`）。
  沒有修改明細模組。

### 與規格 7.2 的差異：帳平檢查改為首頁即時執行（上線審查事項）

- **規格 7.2**：每天 03:30 由 APScheduler 呼叫 `integrity.check_all()`，有問題時在首頁顯示警示。
- **P3-1 實作**：每次開啟首頁時即時呼叫 `integrity.check_all()`；不加入 APScheduler，不新增資料表或設定值。
- **為什麼**：個人資料量小，每次全掃描的成本可以接受；結果永遠是最新的；V1 沒有其他排程工作需要 APScheduler
  （週期性草稿是 V1.5），只為帳平檢查引進排程器與儲存結果的資料表，成本高於效益。
- **差異與代價**：
  1. 沒有開首頁就不會檢查，也沒有「上次檢查時間」或歷史紀錄。
  2. 每次開首頁都掃描全部交易（含已刪除與草稿）；交易量大到首頁變慢時要重新評估。
  3. 檢查失敗（例外）時首頁回 500，不會靜默忽略。
- **上線審查待辦**：正式上線前確認「首頁即時檢查」是否可以取代「每日 03:30 排程」；
  V1.5 引進 APScheduler（週期性草稿）時，再決定是否改回排程並儲存結果。

## P3-2A：信用卡週期 service（F07、T18、規格 8.1）

- **範圍**：`services/credit_cards.py` 新增 `current_cycle()`、`amount_due()` 與純日期函式。
  沒有 migration，不改 router／template／首頁（P3-2B），不碰 LedgerService、EntryBuilder。
  沒有新增 repository 查詢：重用 `ledger_queries.balance()` 與 `ledger_repo.active_sum_for_accounts()`。
- **「本期」的意思**：`current_cycle` 表示「最近已結帳、目前等待繳款的 statement cycle」，
  不是正在累積中的下一期。結帳日之後新刷的消費屬於下一期，不計入本期應繳。
- **週期**：`statement_end` = 最近一個不晚於今天的結帳日；`statement_start` = 上一個結帳日 + 1 天。
  結帳日該月沒有該日時取月底（規格 6.2）。
- **結帳日當天的交易算本期（inclusive）**：依規格 8.1「最近一次結帳日當天的信用卡負債餘額」，
  與 `balance(as_of)` 含當天一致。不依銀行實際入帳日做特殊處理，差異列為已知限制。
- **繳款日**：`due_date` = 最近結帳日之後第一個符合 `due_day` 的日期；該月沒有該日則取月底；
  必須嚴格晚於 `statement_end`（`due_day` 等於結帳日，或月底截斷後等於結帳日時，落在下個月）。
- **公式**：
  `statement_balance = balance(卡, as_of=statement_end)`（欠款為正，含結帳日當天）；
  `paid_since = Σ CARD_PAYMENT 對該卡的分錄，txn_date ∈ [statement_end + 1, 今天]`；
  `raw = statement_balance − paid_since`；`amount_due = max(raw, 0)`；`overpaid = max(−raw, 0)`。
  全部走 `active_postings()`：已刪除、草稿不計入；未來日期的刷卡與繳款不計入。
- **只扣 CARD_PAYMENT**：依 V1 規格，本期應繳只從結帳日餘額扣除結帳日後的 `CARD_PAYMENT`；
  結帳日後的 `REFUND` 不對已結帳金額做跨期重算，因此不在 `paid_since` 中扣除。
  結帳日前的退款已反映在 `statement_balance`。`ADJUSTMENT`、`MANUAL` 同樣不當成繳款。
  這是系統內的計算規則，不代表銀行實際的入帳或退款政策。
- **溢繳**：兩個欄位 `amount_due` 與 `overpaid`，正負號判斷在 service，template 只顯示。
- **逾期**：`days_until_due = due_date − 今天`，已過期為負數；P3-2A 不新增 overdue flag，
  顯示文字留到 P3-2B。
- **邊界**：沒有信用卡設定 → 回傳 `None`（不推測週期）；非信用卡科目 → `RuleViolation("NOT_CREDIT_CARD")`；
  停用的信用卡仍可計算。
- **V1 分期全額入帳**：本金與利息在刷卡當天全額計入，有分期消費時本期應繳會偏高（規格 8.1）；
  不補償，V1.5 的分期追蹤才處理。有測試把這個行為釘住。

### 已知限制

1. **記帳日與銀行入帳日**：系統以交易日期認列，銀行帳單可能以入帳日切分，
   結帳日前後幾天的交易可能與帳單不同。
2. **結帳日沒有歷史版本**：之後修改信用卡設定，過去的週期會被重新切分（只影響顯示，不影響帳務）。
3. **分期偏高**：見上。
4. **上線首個週期的本期應繳可能不精準**：V1 首次上線時，如果信用卡只輸入一個「目前總欠款」的
   opening balance，而這個總欠款同時包含 (a) 最近一期已結帳、應繳的金額，與 (b) 結帳日之後尚未出帳的
   新消費，系統無法只靠單一 opening balance 自動還原這兩部分，所以本期應繳在第一個週期可能不精準
   （單一 opening 晚於最近結帳日 → 本期應繳偏低，且繳款後可能顯示溢繳；回填到結帳日 → 本期應繳偏高）。
   過了第一個結帳日之後，只要期間的繳款都有記，數字就恢復正確。
   - P3-2A **不**為此新增 schema、欄位或特殊計算。
   - **不可**把整筆目前總欠款簡單回填到最近結帳日，那會把結帳後的新消費也錯算成本期應繳。
   - 回歸測試 `test_opening_after_statement_end_is_not_in_statement_balance` 釘住這個行為：
     它記錄的是已知限制，不是要求 service 特判。
   - 這是 P3-7 的待辦，見下。
